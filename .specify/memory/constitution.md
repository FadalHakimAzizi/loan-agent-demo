# Demo Lending Agent Constitution

## Core Principles

### I. Deterministic Money Logic

- The LLM MUST NOT calculate any money value and MUST NOT make the final policy decision.
- Installments, the debt-service ratio, and every policy check MUST be deterministic code that
  uses `Decimal`. `float` MUST NOT be used for money.
- After the AI submits a recommendation, the system MUST re-evaluate the policy. A recommendation
  the policy does not allow MUST be overridden to "refer to human", and the reason for the
  override MUST be recorded with the application.

Rationale: lending decisions must be reproducible and auditable. A language model can make
arithmetic mistakes and can be persuaded; deterministic code cannot be talked into another number.

### II. Human Approval Before Money Moves

- A loan MUST NOT be disbursed without an explicit approval by a loan officer.
- This rule MUST be enforced in the database and the API, not only in prompts.
- Disbursement MUST be idempotent: repeating the same request MUST NOT create a second
  disbursement.

Rationale: money that has left the lender is hard to recover. Enforcing approval below the AI layer
means a bug or a manipulated prompt cannot move money.

### III. Untrusted Input and Privacy

- Applicant free text MUST be treated as data, never as instructions to the agent or the system.
- NIK and phone numbers MUST be masked in logs, traces, and reports.

Rationale: prompt injection is the main attack on an LLM agent, and identity numbers are sensitive
even in a demo. Logs and traces are where personal data most often leaks.

### IV. Synthetic Data and No Secrets

- The project MUST use synthetic data only. Real personal data MUST NOT appear in code, fixtures,
  tests, prompts, or reports.
- Every synthetic NIK MUST start with "00".
- Secrets MUST live in environment variables (or a secret manager when deployed) and MUST NOT be
  committed to the repository.

Rationale: the repository is public. Real NIKs start with a province code, so a "00" prefix makes
every test record recognizably fake. A committed key is leaked the moment it is pushed.

### V. Tests First for Deterministic Logic

- Every policy rule, money calculation, and state transition MUST have unit tests, written before
  or together with the code they test.
- The normal test suite MUST run without any API key, using a scripted fake LLM client.
- Tests that call the real AI model MUST be marked separately and run only on purpose.

Rationale: these parts decide money and status, so they must be proven correct. A suite that needs
no key runs in CI and on both laptops at no cost.

### VI. Evidence-Backed Claims

- Any metric (accuracy, pass rate, cost, or similar) shown in the README or anywhere else MUST come
  from an evaluation report generated by actually running the evaluation.
- Numbers MUST NOT be invented, estimated, or rounded up to look better.

Rationale: this is a portfolio project. One invented number destroys trust in every other claim.

### VII. Verified Dependencies

- Library and SDK usage MUST be checked against current documentation through the Context7 MCP
  server before the code is written. If Context7 is unavailable, the official documentation MUST be
  used instead, and the author MUST say so.
- The LLM API rules in AGENTS.md section 6 are mandatory.
- Documentation queries MUST NOT contain secrets, personal data, or private code.

Rationale: SDKs change quickly. Code written from memory often calls APIs that no longer exist or
sends parameters the model rejects.

### VIII. Visible Core Skills

- The agent loop MUST be our own code that calls the LLM provider's chat API directly. The
  provider and the default model are set in AGENTS.md section 6.
- The credit bureau MUST be our own MCP server, used through our own client adapter.
- A hosted agent service or agent framework MUST NOT replace either of them.

Rationale: the project exists to demonstrate these skills. A framework would hide exactly the parts
an interviewer wants to see.

### IX. Simple and Explainable

- The simplest design that meets the spec MUST be chosen. Any extra complexity MUST be justified in
  the plan's Complexity Tracking section.
- Code MUST be explainable by a junior engineer in an interview.
- Pull requests MUST be small, reviewed by the other person's agent, and merged by a human.

Rationale: two junior engineers maintain and defend this code. Code you cannot explain is code you
cannot own.

## Scope and Constraints

- The project is a portfolio demo for "Demo Lending", a fictional Indonesian lender. It is not
  financial advice and does not claim regulatory compliance.
- The tech stack, repository layout, and language conventions are defined in AGENTS.md section 7.
  Changing them requires agreement from both humans.

## Development Workflow and Quality Gates

- Every feature follows the Spec Kit flow in AGENTS.md section 2
  (specify, clarify, plan, tasks, analyze, implement, converge), with a human review between steps.
- Every plan MUST pass its Constitution Check before tasks are generated.
- A pull request MUST NOT be opened until converge reports Converged and `ruff check`,
  `ruff format --check`, and `pytest` pass. Their real output goes in the pull request description.

## Governance

- AGENTS.md describes the workflow and tech conventions. This constitution wins when they conflict.
- Amendments require agreement from both humans and a version bump:
  - MAJOR: a principle is removed or redefined;
  - MINOR: a principle or section is added, or guidance is materially expanded;
  - PATCH: wording and clarifications.
- Every plan and every pull request review MUST check compliance with this constitution. A
  violation blocks the merge until it is fixed or the constitution is amended.
